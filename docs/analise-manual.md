# Análise Manual

Escala de severidade usada (definida no enunciado do desafio):
**CRITICAL** (segurança grave / God Class) · **HIGH** (violação forte de MVC/SOLID) · **MEDIUM** (duplicação, N+1, validação ausente) · **LOW** (legibilidade, nomes, magic numbers).

## Projeto 1 — code-smells-project (Python/Flask, API de E-commerce)

**Stack:** Python 3 + Flask 3.1.1 + flask-cors 5.0.1 + SQLite (`sqlite3` nativo, SQL cru).
**Estrutura:** 4 arquivos (`app.py`, `controllers.py`, `models.py`, `database.py`), ~780 linhas. Tabelas: `produtos`, `usuarios`, `pedidos`, `itens_pedido`.
**Baseline:** 22/22 chamadas do smoke test (`scripts/smoke-project-1.sh`) respondem com o status esperado antes da refatoração.

| # | Severidade | Problema | Local | Por que é relevante |
|---|---|---|---|---|
| 1 | CRITICAL | **SQL Injection** — SQL montado por concatenação de strings com dados do usuário | `models.py:28`, `47-50`, `57-61`, `109-111`, `126-129`, `280`, `289-297` (e demais queries) | Comprovado no baseline: login com `email = "admin@loja.com' --"` autentica como admin sem senha. Permite ler/alterar/apagar todo o banco. |
| 2 | CRITICAL | **Endpoint que executa SQL arbitrário** sem autenticação (`/admin/query`) e **reset do banco** sem autenticação (`/admin/reset-db`) | `app.py:59-78`, `app.py:47-57` | Qualquer cliente HTTP lê as senhas (`SELECT email, senha FROM usuarios` funcionou no baseline) ou apaga todos os dados. |
| 3 | CRITICAL | **Credenciais hardcoded e vazadas** — `SECRET_KEY` fixa no código e devolvida pelo `/health` junto com `debug` e `db_path` | `app.py:7`, `controllers.py:286-289` | Segredo versionado no git e exposto publicamente; com a chave é possível forjar sessões/assinaturas. |
| 4 | CRITICAL | **Senhas em texto puro** — gravadas, comparadas e retornadas pela API | `database.py:76-78` (seed), `models.py:109-111` (login), `models.py:83` e `99` (`senha` no JSON de `/usuarios`) | Vazamento direto de credenciais de todos os usuários; deveria usar hash (bcrypt/werkzeug `generate_password_hash`) e nunca serializar o campo. |
| 5 | HIGH | **Debug ligado em "produção"** + bind em `0.0.0.0` | `app.py:8`, `app.py:88` | O debugger do Werkzeug permite execução remota de código se exposto na rede. |
| 6 | HIGH | **Regra de negócio fora da camada certa / controller acoplado ao banco** — `models.criar_pedido` faz validação de estoque, cálculo de total e baixa de estoque; `relatorio_vendas` calcula desconto no model; `health_check` faz SQL direto no controller | `models.py:133-169`, `models.py:256-262`, `controllers.py:264-284` | Model mistura acesso a dados com regra de negócio; controller pula o model. Impossível testar a regra isoladamente. |
| 7 | HIGH | **Estado global mutável** — conexão SQLite única global compartilhada entre threads (`check_same_thread=False`), e `get_db()` também cria schema e popula dados | `database.py:4-10`, `database.py:7-86` | Condições de corrida em requisições concorrentes; responsabilidade misturada (conexão + migração + seed). |
| 8 | HIGH | **Efeitos colaterais acoplados no controller** — "envio" de e-mail/SMS/push e notificações via `print` dentro do fluxo HTTP | `controllers.py:208-210`, `controllers.py:247-250` | Deveria ser um serviço de notificação injetável; hoje é impossível trocar/testar. |
| 9 | MEDIUM | **Query N+1** — para cada pedido busca os itens, e para cada item busca o produto | `models.py:187-193` e `models.py:219-225` | 1 + N + N×M queries; degrada linearmente com o volume. Resolver com `JOIN`. |

| 11 | MEDIUM | **Validação ausente / error handling não centralizado** — `request.get_json()` pode ser `None` e `.get` quebra (500); todo controller repete `try/except Exception` devolvendo `str(e)` ao cliente | `controllers.py:170`, `controllers.py:240`; padrão `except Exception as e: return jsonify({"erro": str(e)}), 500` em todas as funções (ex.: `controllers.py:11-12`) | Vaza detalhes internos (mensagens de exceção/SQL) e gera 500 onde deveria ser 400. | 14 | LOW | **`print` como logging** | `controllers.py:8`, `57`, `106`, `162`, `179`, `182` | Sem níveis, sem destino configurável; ainda loga e-mail de usuários. |
| 15 | LOW | **Nomenclatura e imports mortos** — `id` sombreia o built-in, `cursor2`/`cursor3`, `import sqlite3` e `import os` não usados | `controllers.py:14`, `models.py:24`, `models.py:187-191`, `models.py:2`, `database.py:2` | Legibilidade e ruído. |

**APIs deprecated:** nenhuma API obsoleta relevante neste projeto (Flask 3.1 atual; `sqlite3` padrão). A skill deve reportar "não aplicável" em vez de inventar.

## Projeto 2 — ecommerce-api-legacy (Node.js/Express, LMS API com checkout)

**Stack:** Node.js + Express 4.22 + sqlite3 5.1.7 (banco **em memória**, recriado a cada boot), callbacks.
**Estrutura:** 3 arquivos em `src/` (`app.js`, `AppManager.js`, `utils.js`), ~180 linhas. Tabelas: `users`, `courses`, `enrollments`, `payments`, `audit_logs`.
**Endpoints:** `POST /api/checkout`, `GET /api/admin/financial-report`, `DELETE /api/users/:id`.
**Baseline:** 8/8 verificações do smoke test (`scripts/smoke-project-2.sh`) passam antes da refatoração.

| # | Severidade | Problema | Local | Por que é relevante |
|---|---|---|---|---|
| 1 | CRITICAL | **God Class** — `AppManager` cria a conexão, cria o schema, faz seed, registra rotas, valida input, processa pagamento, matricula, audita e gera relatório | `src/AppManager.js:4-139` | Nenhuma separação de camadas; qualquer mudança afeta tudo e nada é testável isoladamente. |
| 2 | CRITICAL | **Credenciais hardcoded** — senha do banco, chave **live** do gateway de pagamento e usuário SMTP no código | `src/utils.js:2-5` | Segredos versionados no git; deveriam vir de variáveis de ambiente. |
| 3 | CRITICAL | **Dados de cartão e chave do gateway escritos no log** | `src/AppManager.js:45` | Comprovado no baseline: o log mostra `Processando cartão 4111222233334444 na chave pk_live_...`. Violação de PCI-DSS. |
| 4 | CRITICAL | **Hash de senha inseguro** — `badCrypto` é Base64 truncado (reversível/colisões triviais) e senha padrão `"123456"` quando ausente; seed com senha em texto puro | `src/utils.js:17-23`, `src/AppManager.js:68`, `src/AppManager.js:18` | Senhas efetivamente em texto puro; usuários criados sem senha recebem uma senha conhecida. |
| 5 | HIGH | **Endpoints administrativos sem autenticação** — relatório financeiro e exclusão de usuário abertos | `src/AppManager.js:80`, `src/AppManager.js:131` | Qualquer cliente lê dados financeiros/nomes de alunos e apaga usuários. |
| 6 | HIGH | **Regra de negócio dentro da rota + callback hell** — o handler de checkout tem 5 níveis de callbacks aninhados com validação, "gateway" de pagamento (`cc.startsWith("4")`), matrícula, pagamento e auditoria | `src/AppManager.js:28-78`, `src/AppManager.js:46` | Fluxo ilegível, impossível testar a regra de pagamento; deveria ser service/controller com `async/await`. |
| 7 | HIGH | **Checkout sem transação** — matrícula, pagamento e auditoria são inserts independentes | `src/AppManager.js:50-61` | Se o insert do pagamento falha, a matrícula fica criada sem pagamento (estado inconsistente). |
| 8 | HIGH | **Estado global mutável** — `globalCache` e `totalRevenue` de módulo (o segundo é exportado como primitivo e nunca atualizado) | `src/utils.js:9-10`, `src/utils.js:14` | Cache cresce sem limite (memory leak) e é compartilhado por todas as requisições; `totalRevenue` é código morto enganoso. |
| 9 | MEDIUM | **Query N+1** no relatório — para cada curso busca matrículas; para cada matrícula busca usuário e pagamento | `src/AppManager.js:89-106` | 1 + C + 2×M queries; resolvível com um `JOIN` + `GROUP BY`. |
| 10 | MEDIUM | **Exclusão sem integridade referencial + erros ignorados** — `DELETE` não remove/verifica matrículas e pagamentos, ignora `err` e sempre responde 200 (mesmo para id inexistente) | `src/AppManager.js:131-136` | Comprovado no baseline: após o delete o relatório mostra `"student":"Unknown"` (dados órfãos). |
| 11 | MEDIUM | **Erros de callback ignorados** — `err` não é verificado antes de usar o resultado (`enrollments.length` com `enrollments` indefinido derruba o processo); erro da auditoria é engolido | `src/AppManager.js:92-93`, `104`, `106`, `57` | Uma falha de banco vira crash do servidor em vez de resposta 500; não há error handler central do Express. |
| 12 | MEDIUM | **Validação de entrada ausente/fraca** — `pwd` opcional, sem validação de formato de e-mail, cartão ou tipo de `c_id` | `src/AppManager.js:29-35` | Dados inválidos chegam ao banco; o contrato da API não é explícito. |
| 13 | MEDIUM | **Dependências desatualizadas com vulnerabilidades conhecidas** — `npm audit`: 13 vulnerabilidades (2 critical, 8 high), via `express@4` (`body-parser`, `path-to-regexp`, `proxy-addr`, `qs`) e `sqlite3` (`tar`) | `package.json:10-11` | Recomendado atualizar para Express 5 / versões corrigidas. |
| 14 | LOW | **Nomes crípticos** — variáveis `u`, `e`, `p`, `cid`, `cc` e payload `usr`, `eml`, `pwd`, `c_id` | `src/AppManager.js:29-33` | Legibilidade; o contrato do payload deve ser mantido por compatibilidade, mas mapeado para nomes claros internamente. |
| 15 | LOW | **Magic numbers/strings e respostas inconsistentes** — porta `3000` fixa, loop de `10000`, prefixo `"4"`, status `'PAID'`/`'DENIED'` soltos; erros ora em texto (`res.send("Bad Request")`) ora em JSON | `src/utils.js:6`, `src/utils.js:19`, `src/AppManager.js:46`, `src/AppManager.js:35` | Regras escondidas e clientes precisam tratar formatos diferentes de erro. |
| 16 | LOW | **`const self = this` misturado com arrow functions e `function`** + import não usado (`totalRevenue`) | `src/AppManager.js:26`, `src/AppManager.js:2` | Confusão de escopo de `this` (o código usa `this.lastID` e `self.db` no mesmo bloco). |

**APIs deprecated:** o código-fonte não chama APIs removidas do Node (usa `Buffer.from`, não o obsoleto `new Buffer`). Porém o estilo **callback** de `sqlite3` é legado frente a `async/await` (Promises), e as dependências estão desatualizadas (item 13). A skill deve tratar isso como "API legada/outdated" com recomendação moderna.

## Projeto 3 — task-manager-api (Python/Flask, API de Task Manager)

**Stack:** Python 3 + Flask 3.0.0 + Flask-SQLAlchemy 3.1.1 (SQLAlchemy 2.x) + flask-cors + SQLite (`instance/tasks.db`).
**Estrutura:** já separada em `models/`, `routes/` (Blueprints), `services/`, `utils/` — 13 arquivos `.py`, ~1.150 linhas. Tabelas: `users`, `tasks`, `categories`.
**Baseline:** 32/32 chamadas do smoke test (`scripts/smoke-project-3.sh`) respondem como esperado antes da refatoração (após `python seed.py`).

| # | Severidade | Problema | Local | Por que é relevante |
|---|---|---|---|---|
| 1 | CRITICAL | **Credenciais hardcoded** — `SECRET_KEY` e usuário/senha SMTP no código | `app.py:13`, `services/notification_service.py:7-10` | Segredos versionados no git. |
| 2 | CRITICAL | **Hash de senha fraco (MD5 sem salt) e hash exposto na API** — `to_dict()` inclui `password`, retornado por login, criação, atualização e consulta de usuário | `models/user.py:29`, `models/user.py:32`, `models/user.py:21`; uso em `routes/user_routes.py:33`, `85`, `129`, `209` | Comprovado no baseline: o login devolve `"password": "81dc9bdb52d04dc20036dbd8313ed055"` (= MD5 de `"1234"`, quebrável em segundos). |
| 3 | CRITICAL | **Autenticação inexistente + escalação de privilégio** — token falso `'fake-jwt-token-' + id`, nenhuma rota exige autenticação, e `POST /users` aceita `role: "admin"` do próprio cliente | `routes/user_routes.py:210`, `routes/user_routes.py:52`, `routes/user_routes.py:71-72` | Comprovado: qualquer cliente se cadastra como `admin`. |

**Observação arquitetural:** este projeto prova que "ter pastas `models/` e `routes/`" não é o mesmo que seguir MVC. A Fase 3 aqui deve ser **incremental**: manter a estrutura existente, introduzir `controllers/` (ou services de verdade) e `config/`, e mover a lógica das rotas, em vez de reescrever o projeto como se fosse um monolito.
